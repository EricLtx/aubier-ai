# Trusted computing base statement (spec §5)

In scope of the invariants: the kernel daemon, its service account, the OS keyring, the interceptor chain, kernel-launched (governed) inference processes, enrolled device keys.

Outside the TCB, per platform, and surfaced in the inventory as **unmediated channels**:
- any harness that the platform cannot confine (no Job Object/AppContainer, landlock or sandbox-exec available) — it may read the store directly;
- SaaS assistants embedded inside third-party applications;
- ungoverned inference engines not launched by the kernel.

Any object reachable by an unmediated channel is treated as projected to that channel's clearance for I2 purposes; the UI says so.

## Arch adapters (SP1b)

### Claude Code adapter

Pure completion, no tools. The kernel launches the installed `claude` with every built-in tool removed (`--tools ""`), MCP connectors off (`--safe-mode --strict-mcp-config`), one turn (`--max-turns 1`) and no session written to disk (`--no-session-persistence`); the prompt goes in on stdin, so no process list on this machine shows it. The child runs in one fixed, empty directory (`<state_dir>/claude-code-cwd`, `0700` on Unix), which is also the only directory it could reach if a tool were ever re-enabled.

**The binary is daemon configuration, validated at start (founder decision 2026-10-13, closing final review I-1's open item; Rulings 41 and 43).** Like the harness binary (`vkd --harness-bin`, Ruling 20), the arch's `claude` is the daemon's: `vkd --claude-bin <path>` (passed on by `vk boot --claude-bin`, and written into the service's `ImagePath` by `vkd-service install --claude-bin`). It is **not** a field of the `arch.mount` request — a request that names `binary` is refused as a bad request that says where the binary is set, and `vk mount claude-code` has no `--bin` — and it is **not persisted in the mount spec**. It is checked **once, when the daemon starts**, before the store is opened, and a refused path is a start that fails, naming `--claude-bin` and the rule; the daemon then runs the pinned path at mount (`claude --version`, for the arch id), at every boot that re-creates the arch, and at every inference — under the Windows service, **as `NT SERVICE\vkd`**. The rule is the one SP1b applied to the mount field, moved: a bare name (`claude`, the default) is looked up on the *daemon's* own `PATH` — as `claude.exe` on Windows, never a `.cmd` shim — **at start**, and pinned there to the resolved path of what was found, which is then held to the rule below. An explicit name that is not there is refused; so is the default **under the service**, which pins its binary at start or does not run (fix round 1, I-1). Only an **interactive** daemon may start with the default unfound (a warning): it then looks the name up again **at each `claude-code` mount and each boot re-creation**, by the same rule, and pins the resolved path into that arch's adapter, or refuses the mount while it is still not there. **No adapter is ever handed a bare name: after start, no `PATH` lookup happens at call time**, only at those two moments and only on an interactive daemon that found nothing at start; a path is **resolved** — every symlink and junction followed, canonicalised, the `\\?\` prefix removed — and the resolved path, not the spelling, is what is checked and run. **On every daemon** it must be absolute, have no `..` component, and resolve (a link loop does not) to a file that exists; a link is not itself refused. **Under the Windows service only** (`vkd --as-service`), it must be on a local fixed drive — a UNC share in either spelling, a device path, or a removable or network-mapped drive is refused, by its spelling before anything is opened and again on the resolved path (final re-review N-2) — and the resolved path is also refused inside a synced folder or under a user profile — the rule `vkd-service install` applies to its own `ImagePath` — because the service would run a file the user's processes can replace as `NT SERVICE\vkd`. A bare name found on the service's `PATH` is held to the same rule. An **interactive** daemon is the user's own process, in the user's own trust domain, and may run the user's own profile-installed or synced binary (Ruling 43). `vkd-service install --claude-bin` applies the service's rule before the service exists and refuses a `--claude-bin` given after `--`, which would reach the service unchecked. **SP1b mount specs:** a spec persisted by an SP1b `arch.mount` still carries the `binary` its request named; it is accepted on read, the field is **ignored** — the daemon's binary is what runs — and each boot that re-creates the arch logs a warning naming the ignored path. There is no migration step; mounting the arch again writes a spec without the field. The config is a closed shape (`deny_unknown_fields`, Ruling 42). **Open item (founder):** an **ancestor-ACL check** — the binary and every directory above it writable only by Administrators, SYSTEM or TrustedInstaller — is not made: the path rules above say *where* the binary is, not who may write there, so a binary in an ordinary-user-writable directory outside any profile (`C:\tools\`) still passes. Neither the harness binary nor `vkd-service install` makes that check either.

The inference itself is **not governed**: it happens on Anthropic's servers, where no interceptor of ours runs. The manifest says so — `governed: false`, `locality: Cloud`, `jurisdiction: "US"`, `retention_days: 30`, clearance capped at Business with third-party data refused — so I2 refuses to lower anything above that into it. **Egress to Anthropic is not observed in SP1b**: this node records what it sent and what came back, not what the far end did with it.

Subscription use is the founder's own. A claude.ai subscription is a person's, not a product's: nothing is billed per call, so the manifest's `cost_per_1k_tokens_eur` is `0` and the list-price equivalent the CLI reports rides on the `infer` event as `cost_list_usd` — and, since SP1b Task 8, on the per-call usage row and the per-arch counters `vk top` and `vk task show` print — visibly a comparison and not a charge. **Customer nodes use API arches** (task 2b), which carry a key, a per-token price and, for the EU jurisdiction, a different host.

### Anthropic API adapters — first-party (US) and Bedrock (EU)

The arches a **customer** node mounts, where the Claude Code adapter above is
the founder's own subscription. Both are ungoverned cloud arches — `locality:
cloud`, `governed: false`, clearance capped at Business with third-party data
refused — and both are metered, unlike the subscription arch. The first-party
one carries Anthropic's list price in its manifest (`cost_per_1k_tokens_eur`,
converted at a pinned and dated rate) and the USD figure on every call;
Bedrock is priced by AWS, whose list this node has not read, so that arch's
price is `None` rather than a figure from the wrong table. `cost_per_1k_tokens_eur`
is `Option<f64>` for exactly this (Ruling 30): `Some(0.0)` is the claim a
local model and a subscription make — nothing is billed — while `None` is the
absence of a claim, and `vk top` prints `?` for it. A `?` rendered as `0`
would tell an operator their EU calls were free.

`vk mount anthropic` posts `/v1/messages` to `api.anthropic.com` over raw
HTTPS (rustls, a connect timeout and a call timeout, and *with* the machine's
proxy configuration honoured — the opposite of the Ollama adapter, because a
proxy on the path to a public API is how many networks reach it at all and the
manifest already says the register leaves the node). Header
`anthropic-version: 2023-06-01`, `thinking: {"type":"adaptive"}`, no
streaming, `max_tokens` bounded at 4096 — and `thinking` **only** for a model
the table marks as taking it, because adaptive thinking arrived with the
4.6/5 generation and `claude-haiku-4-5` 400s on it — and the answer is the
response's
`text` blocks concatenated — never `content[0]`, because a thinking block sits
in front of them. Manifest: `jurisdiction: "US"`, `retention_days: Some(30)`.
`vk mount bedrock` is the same models through Bedrock's `Converse` in
`eu-central-1` or `eu-west-1` — **those two regions and no other, refused at
the door**, because the manifest's `jurisdiction: "EU"` *is* the region —
with `retention_days: None`, since AWS stores neither the inputs nor the
outputs. Its transport is behind the `bedrock` cargo feature, **off by
default** (Ruling 30): the 83 extra crates it brings — `aws-lc-sys` among
them — do not belong in the trusted base of every node for an arch most never
mount, and the default build refuses that kind by name and says how to get
one that has it.

**Mounting either of them is a human act (I1).** `arch.mount` of any kind
whose manifest says `locality: cloud` — `anthropic`, `bedrock` and
`claude-code` — requires the same presence proof `stop`, `resume` and
`approve` require, and is refused from a bare machine principal. The reason
is I2's third-party rule: a cloud mount authorises this node's registers to
leave the machine, and it does so durably, because the mount spec is replayed
at every boot. The refusal happens twice, on purpose: once on the kind — with the
proof fully verified, signature and nonce, *before* this daemon reads its
keyring, walks an AWS credential chain or runs `claude --version` for a caller
who may have forged it — and once on the built adapter's own manifest, so a
future cloud kind nobody added to the list is caught rather than admitted.
**The boot replay takes no proof and is not meant to:** re-creating a
persisted arch goes through `adapter_factory`, which the kernel calls
directly and which never enters the RPC dispatch at all. The human authorises
the mount once and the authorisation is durable because the spec is; an
unattended restart is not a second authorisation and has nobody to ask.

**Where the key is sent is the daemon's to decide, not a caller's.** The
first-party origin is fixed at `https://api.anthropic.com`; the mount config
for a cloud kind is a closed shape (`deny_unknown_fields`), so `base_url`,
`endpoint` or any other name a caller invents is a `-32602` that names the
field rather than a host this daemon then posts its key to. Only
`vkd --anthropic-base-url` moves it, it exists for tests, and it must itself
be `https://` or this machine's own loopback. Redirects are not followed
(`redirect::Policy::none()`): reqwest strips `authorization` and four other
headers across a host change and `x-api-key` is on none of those lists, so a
`307` would otherwise hand the key and the POST body to whatever it named.
`context_ceiling` and `timeout_secs` are clamped rather than taken as given —
`context_ceiling` is a manifest field outside `ArchIdentity`, so an unclamped
one would let a caller mount an arch claiming a four-billion-token window
under an ordinary-looking arch id and leave I4′ bounding nothing.

**The key is in the OS keyring and in no other place.** Service `vk`, user
`anthropic`, put there by `vk secret set anthropic`, which prompts with the
terminal's echo off and never prints the value back. It is not in the mount
spec — a spec is stored unencrypted in the metadata database, and
`MountSpec::new` refuses a config carrying anything credential-shaped — not in
a manifest, not in a log line and not in an error: every message these
adapters produce is passed through a scrub that removes the key, the type that
holds it prints as `SecretString(redacted)`, and its bytes are zeroed when the
adapter is dropped. The daemon reads the keyring at mount and again whenever
it re-creates a persisted arch at boot, which is what makes rotation a `vk
secret set` and a restart. `vkd --anthropic-key-file` is the one file seam,
for CI, for a headless node with no credential store, and for the Windows
service account — whose keyring is its own and not the interactive user's, so
`vk secret set` run by that user does not reach it. A key in a file is a key
everyone who can read the file has, so the daemon refuses to start on one that
is not private: mode `0600` on Unix, and on Windows a DACL whose owner and
every entry is this account, SYSTEM or the local administrators — the same
rule, and the same audit, the state directory is held to.

**I4′ on a provider that refuses rather than truncates.** The ceiling is the
model's documented context window (1 000 000 for the Claude 5 family, from
Anthropic's published tables; `--ctx` pins a smaller one), a prompt past nine
tenths of it is refused before anything is sent, and the answer's own
`usage.input_tokens` is checked against the ceiling afterwards. The pre-check
count is the API's own `/v1/messages/count_tokens`, falling back to the
`bytes/3 + 64` estimate when that call fails — a rate-limited counter should
cost accuracy, not the inference. The estimate, not the API, is what
`count_tokens` reports to the kernel's projection loop: that loop asks once per
candidate line, and each of those would otherwise be an HTTPS round trip. The
estimate runs high, so a prompt the kernel fitted by it is one the measured
count also fits.

**What has not been exercised.** There is no API key and no AWS credential on
the machine these adapters were written on, so every test is against a
loopback stand-in and **no call has ever been made to either provider**. For
Bedrock in particular the request shape, the `eu.` cross-region
inference-profile prefix and the credential-resolution path are pinned by unit
tests and by AWS's documentation, and by nothing that has run.

### Ollama adapter

The first **governed** arch, and the only one so far: the kernel starts the container itself (`docker run -d --name vk-ollama -p 127.0.0.1:11434:11434 -v vk-ollama:/root/.ollama --memory 12g --cpus 6 ollama/ollama:0.33.3`), so the inference is a process this node launched, capped at 12 GiB of memory and 6 CPUs, published on loopback only, with the weights in a volume it owns. `governed: true` is claimed only after the caps have been read *back* off the running container (`HostConfig.Memory`, `HostConfig.NanoCpus`): a container running without them is not a governor, whatever it was meant to be started with, and an existing `vk-ollama` whose image or caps are not the ones this mount asks for is refused rather than adopted — the remedy, `vk mount ollama --recreate`, replaces it and keeps the volume. A mount is also refused when a foreign process already answers on the published port while that container is stopped, because the identity would otherwise be read off somebody else's server.

`vk mount ollama --external URL` mounts an Ollama this node did not start — that one is `governed: false`, clearance capped at Business with third-party data refused, and it is an **ungoverned inference engine** in the sense of the list above. `URL` must be loopback (127.0.0.0/8, `::1`, `localhost`): an engine on another host is a register crossing the network under a manifest that still says `locality: Local`, and that arrives with SP4. The check parses the URL with the `url` crate — the parser the HTTP client uses — through the one helper the Anthropic base-URL check uses too (`vk_kernel::arch::origin_loopback`, final review I-4), so `http://evil.example\@127.0.0.1:11434` is read as `evil.example` and refused, where the earlier hand-written scan read it as loopback.

**What a request may say (Ruling 42).** The Ollama mount config is a closed shape (`deny_unknown_fields`): a field it does not have is refused by name. `memory` and `cpus` reach `docker run`'s argv, so they are held to plain formats first — memory `^[0-9]+[kmg]?$`, cpus `^[0-9]+(\.[0-9]+)?$` — and anything else is a bad request. The **image** is the daemon's, pinned (`ollama/ollama:0.33.3`, digest `sha256:32931b46…`): a request may repeat it by tag, by digest or both, and any other image is refused. The image is checked before any proof is asked for (final re-review N-1), so the pinned image named by digest mounts like the default and a foreign one is refused outright. Mounting with `--external` is a **human act** like a cloud mount: the proof is verified before the adapter is built, and the loopback rule above still applies to the URL.

Nothing about a governed call leaves the machine: `locality: Local`, `jurisdiction: "local"`, `retention_days: 0`, clearance up to Personal, `cost_per_1k_tokens_eur: 0` and no `cost_list_usd` — a model on this CPU is not billed and has no list price to compare against. That claim is underwritten, not assumed: the adapter's HTTP client is built with `no_proxy`, so `HTTP_PROXY`, `ALL_PROXY` and the platform's own proxy settings cannot route a loopback prompt through a third party. What is **not** claimed: the container is a resource governor, not a sandbox around what the model says. Nothing inspects the completion.

Identity is content-addressed — the arch id hashes the weights' digest from `/api/tags`, the family, parameter size and quantisation, the Ollama version, `num_ctx`, the seed, the digest of the **container image** actually running, and whether the arch is **governed**. The cap *values* are deliberately outside it: the same model under a tighter cap is the same model, only slower, and they are recorded on the mount and on every call's `details` instead. `governed` is inside it because a capped container and an uncapped one carry different clearances (Personal against Business) and different retention, and two manifests that disagree about that must never be able to share an id.

**Its context ceiling is half the window asked for.** Ollama 0.33.3 cuts an oversize prompt to `num_ctx / 2 + 3` tokens and answers HTTP 200 with `done_reason: "stop"` and no error (spike 1a). So the manifest's ceiling is `min(num_ctx, context_length) / 2`; a prompt past nine tenths of that is refused before the call, and an answer whose `prompt_eval_count` reached **that same ceiling** is refused after it — the ceiling, not `num_ctx / 2`, which is the wrong number whenever the model's own window is the binding half. Both are I4′: a confident answer to half a question is the failure this invariant exists to prevent.

## Human ceremony (SP1b, Task 5)

Two ceremonies make a request human, and they share one verifier in the kernel.

- **The kernel mints every approval challenge.** A human approval of a task names a `Challenge{resource: "task:<id>", action_digest: <the task's approval subject>, nonce, expires_at_ms}`, and the only place one comes into being is `RealKernel::mint_approval_challenge` — over the pipe as `approval.challenge {task_id}`, or inside the passkey page's `start`. The nonce is 32 random bytes, the expiry two minutes, the subject the scheduler's own (`task.subject`'s rule), and nothing is minted for a task that is not waiting at its `Approve` step. `approve` — the node-key path — spends the presented challenge **before** it looks at the principal or the signature: it must be, field for field, one this kernel minted, unspent and unexpired, or the call is `E_INVARIANT` and nothing is appended; a challenge that fails any later check is spent all the same, so it cannot be shown again. The map of open challenges is in memory, bounded, and empty after a restart. What SP1a allowed — the client building `Challenge` itself, choosing its own subject, nonce and expiry — is refused now, with a valid signature or without one.
- **Passkeys (WebAuthn).** `vkd` serves two pages on loopback — `127.0.0.1:<port>` **and** `[::1]:<port>` (`--web-port`, default 7734; never a routable address) — at the origin `http://localhost:<port>` with relying-party id `localhost`, the one hostname a browser treats as a secure context over plain HTTP. `vk passkey enroll` opens `/enroll`, where `navigator.credentials.create` asks Windows Hello (or a phone) for a passkey; the daemon verifies the registration in-process with `webauthn-rs` and enrols the credential as device `passkey:<credential id>` with `trust_class: "passkey"` (`device.enrolled`). `vk approve <task> --passkey` opens `/approve/<task>`, whose `start` has the verifier generate the WebAuthn challenge and then has the kernel mint the task's approval challenge **with that value as its nonce** — one value: the kernel binds it to the subject, the resource and a two-minute expiry, and the authenticator signs it inside `clientDataJSON` — keeping the two under one single-use state id. `finish` verifies the assertion with `webauthn-rs` (origin, rp id, the challenge, the signature over `authenticatorData || SHA-256(clientDataJSON)` with the enrolled public key, user verification required, the signature counter), checks once more that the signed challenge is the minted nonce, and only then calls `RealKernel::record_verified_human_approval` — an in-process method no syscall reaches — with `Approval{approver: Human{passkey:…}, challenge: <the minted one>, signature_hex: <the assertion's signature>}` and the assertion itself (credential id, `authenticator_data`, `client_data_json`). That spends the minted challenge, appends `approval.recorded` with `proof: "webauthn"` and the assertion hashed into the payload (the node-key path writes `proof: "device-key"` and no assertion), and stores the assertion row beside the approval row, together or not at all. **What the record proves:** with the approval row, the assertion row and the enrolled public key in the `devices` row, anyone re-verifies the recorded signature and reads the minted nonce out of the signed client data — the same standing a node-key approval has; the flow test does exactly that. The page then runs the one step that was waiting, and only if the task is still waiting at its approve step for that subject. The client supplies an assertion; it never supplies a principal and never a challenge — there is no request field for either.
- **What protects the pages, and from whom.** Loopback HTTP has no ACL: any local process, of any user, can connect to the port. Three things stand between it and the ceremony. (1) `vkd` holds **both** loopback addresses and refuses to start if either is taken — a browser asked for `localhost` may connect to `::1` before `127.0.0.1` (this machine's resolver orders them that way), and an address the daemon did not hold was one a rogue local listener could, and in the review's experiment did, receive the founder's link on; a host with no IPv6 loopback at all is served on IPv4 alone, since `localhost` cannot resolve to `::1` there and nobody can bind it either. (2) Every page and every call carries a link token minted only over the kernel's endpoint (`web.link`): 32 random bytes, ten minutes, bound to a page and, for approvals, a task, spent by the ceremony it served; ceremony state ids are random and single-use; there are no cookies. A request without a live token gets `404` and nothing else. (3) Every request's `Host` must be `localhost`, `127.0.0.1` or `[::1]` on the pages' own port (else `400`), so a page on another origin whose name is rebound to loopback reaches nothing — and `webauthn-rs` would refuse an assertion made on any origin but `http://localhost:<port>` regardless. The token rides the URL's query, where the browser's history keeps it for those ten minutes; the pages send no referrer and load no third-party resource. What a local process of another user can still do: connect, and be told `404`.
- **Enrolment is a human act.** `web.link {page: enroll}` is minted only under a presence proof by an enrolled device key — the node's own key today, which `vk passkey enroll` signs with — so a same-user process that has the pipe and nothing else cannot enrol a passkey of its own. What such a process can still do is what SP1a lets it do: sign with the node key if that key sits in the interactive user's keyring, and that is the SP1a trust model (the interactive user is the operator). The parts that close it are separate: other local users are kept off the endpoint by Task 6's pipe DACL; the harness child is bounded by the Job Object and the permission fence, with a stronger mechanism to come under the execution context contract (see "Execution context contract" below); enrolment under an *enrolled passkey's* assertion or the business admin key (spec §3.6), and revocation, are not yet scheduled — until then the remedy for a credential that should not be there is the `devices` table.
- **What is not claimed.** The authenticator's *attestation* is not verified (`attestation: none`): a passkey is trusted because it was enrolled under an existing human ceremony, not because of what made it — a software passkey enrolled under the node key's presence is as enrolled as Windows Hello is. What Task 5 changes is that the *human key* can now live in a TPM or on a phone rather than in the user's keyring, and that no client anywhere chooses what a human signs. `webauthn-rs` verifies with OpenSSL, built from source into `vkd` (`openssl/vendored`); the verifier's own correctness is that library's.
- **The harness reaches none of this.** No `harness.*` method mints a challenge, takes a presence proof, enrols a device or approves; a harness's `vk_request_approval` writes an open question on the register and nothing more.

## Harness (SP1b, Task 4)

The **harness** is different from the Claude Code *arch*: the arch is a tool-less completion, the harness is Claude Code run as an agent *with* tools, confined, for a `StepKind::Harness` step. It reaches the kernel only through one stdio MCP server (`vk-mcp`), launched under a lease and authenticated by that lease's *token* — a secret the kernel mints for the run, distinct from the lease id, that every `harness.*` syscall carries; the kernel maps the token to the lease and to a machine principal at the harness clearance (up to Business, third-party data refused) and answers as if the harness itself had called. An unknown or expired token is refused (I1 → `E_INVARIANT`), and no `harness.*` method accepts a presence proof — a lease is a machine capability, not a human's presence.

**SP1b harness confinement = Claude Code's own permission enforcement + the Job Object + observed egress. Filesystem isolation of the harness *process* is not claimed. What stands in its place is the execution context contract (see below), which is bounded and improved continuously after the MVP. There is no workspace ACL on Windows, and none is claimed.**

- **What the harness may touch: Claude Code's permission system, locked down (Rulings 19 and 22).** The session runs `--permission-mode dontAsk --permission-prompts none` — Claude Code's documented mode for unattended runs, in which every tool call that would prompt is denied and never retried — with a `settings.json` of the kernel's own passed by `--settings` and `--setting-sources ""`, and under `--restricted`. Its `allow` rules are `Read(./**)`, `Edit(./**)` and `mcp__vk__*` — `Read` and `Edit` being the two rule kinds Claude Code consults for every file tool (`Write`, `Glob` and `Grep` path rules are accepted and ignored, per its documentation; `Edit(…)` covers Write, `Read(…)` covers Glob and Grep). Its `deny` rules remove **every other built-in tool by name**: the 48 that the tools reference and `claude --help` document on 2.1.281, less the five file tools those two rule families govern (`Read`, `Edit`, `Write`, `Glob`, `Grep`) and the two that reach only the session's MCP servers (`ToolSearch`, `WaitForMcpServers`) — so the shell, code and web tools (`Bash`, `PowerShell`, `REPL`, `WebFetch`, …), the agent tools (`Agent`, `Workflow`, `SendMessage`, …), and the ones that reach the user's claude.ai account, device or inbox with no prompt (`RemoteTrigger`, `SendUserFile`, `Artifact`, `PushNotification`, `LSP`, …); a unit test diffs the deny list against the documented list, so a tool the CLI grows fails a test until it is denied. They also keep the projected inputs read-only (`Edit(TASK.md)`, `Edit(PLAN.md)`, `Edit(BRIEF/**)`), forbid writing any settings, MCP or `CLAUDE.md` file (so a run cannot widen its fence or plant one for the next), and name by real path the run's configuration directory, the daemon's store, keys, ledger and exports, the OS and program directories, and the usual sensitive trees under the home directory (`~/.ssh`, `~/.aws`, `~/.claude`, …). The home directory as a whole is *not* denied: the workspace lives under it (`%LOCALAPPDATA%`), and Claude Code's carve-outs cannot reach past a `~/` anchor — so everything else outside the workspace is denied by the mode, not by name, and, since Ruling 22, by two controls of the CLI that do not depend on the mode: `permissions.blockReadsOutsideWorkingDirectories: true` (v2.1.257+: `Read`, `Grep`, `Glob` and `LSP` refuse a path outside the working directories in every permission mode) and `--restricted` (v2.1.248+: the command- and code-running tools and `WebFetch` removed, the file tools confined to the working directories, only managed settings and `--settings` loaded, `bypassPermissions` and cloud sessions refused). `--setting-sources ""` is read as "load no user, project or local settings file": that is inferred from the flag's description (a comma-separated list of the sources to load) and from its parsing on 2.1.281 — the documentation does not state the empty case — and `--restricted` is the documented form of the same guarantee, the belt to that suspender. Managed (admin) settings apply under both. `--strict-mcp-config` keeps every MCP server but the kernel's `vk` out. The run's `mcp.json` (endpoint and token) and `settings.json` are written to `<state_dir>/harness/<task_id>.mcp/`, **outside** the workspace, denied by path, and removed at settle. Proved with a real run under the Ruling 19 fence (Task 4 fix report): a prompt that tried to read `C:\Windows\win.ini`, write a file under `%TEMP%` and read its own `mcp.json` got all three refused in `permission_denials` and still produced its proposal; the two Ruling 22 controls are verified against the installed CLI's own parser (Task 4 review M19: not against `claude doctor`, which does not inspect settings content and was never evidence for the fence), and MCP loading and the allow rules were themselves exercised under `--restricted` in that run.
- **Operator-only seams.** Two variables of the daemon's *own* process environment — never a request field, so no pipe client reaches them — change what every harness is told: `VK_HARNESS_PROMPT_SUFFIX` is appended to the harness prompt, `VK_HARNESS_SYSTEM_SUFFIX` rides `--append-system-prompt`; both print on the `--dry-run` launch line. They are of the same class as `VK_DOCKER` (the arch's container seam) and exist so the fence can be tested from the operator's side of the prompt — a "try to read `C:\Windows\win.ini`" placed in a task's files is content the model refuses as an injection, which proves its judgement and nothing about the fence. Empty in every ordinary run.
- **What that enforcement is not: OS isolation of the process.** It is Claude Code refusing its *own* tool calls. A helper process the model cannot launch (no `Bash`), or a compromised harness binary, would not be bound by it; nothing at the OS level yet stops the harness process from reading what the interactive user can read. Closing that gap is what the execution context contract below is for.
- **Execution context contract (re-recorded 2026-10-13; formerly the open item "Task 10 group G, restricted token").** The question was never one mechanism but where each kind of code runs, so it is recorded as a contract, bounded and improved continuously after the MVP rather than left open until one mechanism works. (1) *Deliberate steps* — a harness the human chose to run — run in a separate, normally launched instance in the user's own session, with a dialog guard (a prompt the run raises is surfaced to the human, never answered by the harness). (2) *AppContainer-style isolation is reserved for model-driven code that needs no application access* — pure completion and the MCP façade — where a LowBox token costs nothing the code needs. (3) *The Job Object and the permission fence remain the shipped confinement* (the fence above, the Job Object, observed egress); nothing here weakens them, and no OS-level filesystem isolation of a deliberate step is claimed. (4) *The restricted-token mechanism and its ignored characterisation tests stay in the tree as reference* (`crates/vk-harness/src/restrict.rs`, `crates/vk-harness/tests/restricted.rs`); they are not wired into the launch. The measurement that led here follows, unchanged. Spike 4a(iii) showed the *mechanism* works from an ordinary session: `CreateRestrictedToken` on the daemon's own token followed by `CreateProcessAsUserW` runs a restricted child (the "restricted token of the caller's own token" case needs no `SeAssignPrimaryToken`; `CreateProcessWithTokenW` needs `SeImpersonate`, which the session lacks). Group G built that mechanism (`crates/vk-harness/src/restrict.rs`) and measured its limit on this machine (2026-09-27, `windows` 0.62.2): a **deprivileged** child (no restricting SIDs) runs with exit `0`, but the moment a restricting SID set that could deny the sensitive objects is applied — every set up to `{RESTRICTED, Users, Everyone, Authenticated Users, logon}`, with `RESTRICTED` also granted on the window station and desktop — a normal Win32 child (`cmd.exe`, and a bare Rust console `.exe`) dies at initialisation with `0xC0000142` (`STATUS_DLL_INIT_FAILED`), and with `logon`, `Users` or `Authenticated Users` as the only restricting SID with `0xC0000022` (`STATUS_ACCESS_DENIED`). **The denying object was not isolated**: no Process Monitor or ETW trace was taken and the DACLs of the session and global namespace objects were not read. What is *inferred* from the exit codes, the ACLs that were read (`System32` grants `Users` and the two AppContainer SIDs and no entry names `RESTRICTED`; the profile's ancestors grant no group SID) and the grants tried is that process initialisation must also reach session/global namespace objects (`\Sessions\N\BaseNamedObjects`, `\KnownDlls`, the CSR port) that grant none of those SIDs for the *restricting* check. The conclusion does not rest on the inference: no per-harness grant (workspace, config directory, window station, desktop) let the child initialise, so every remaining candidate is session- or machine-global. The two ways forward — grant a restricting SID on those namespaces (a **session/machine-global** change) or switch to a **LowBox/AppContainer** token (a **different mechanism** from the spike's) — are each a founder decision, so Task 10 reported group G `NEEDS_CONTEXT` and did **not** ship it, wire it into the launch, or weaken the fence to force it; the founder's answer of 2026-10-13 is the contract above. Two latent spawn items are parked with the decision, not done: the child inherits every inheritable handle of the daemon (`bInheritHandles`) rather than a `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` of its three, and the module's split into token, spawn, icacls and window-object parts; the containment race is closed already (the child is created suspended, contained in the Job Object, then resumed — Task 10 review, Minor 10). The characterisation is pinned by `#[ignore]`d tests in `crates/vk-harness/tests/restricted.rs`; the window-station/desktop grant they make is held by a guard that copies both DACLs first and sets them back, byte for byte, when it drops — a failing assertion included — so the tests leave no session-global state behind, and a run killed before its guard could restore can be cleaned by the exact-match strip the same module provides — which matches an entry's shape, not its origin: a fresh logon session on this machine already carried `RESTRICTED` entries of the shapes it removes before any grant was made in it (measured 2026-10-13), so it is run by hand, only on entries known to be a leftover — and there is no command for it: it is reached only by calling `vk_harness::restrict::strip_restricted_from_winsta_desktop` from a scratch program after reading both DACLs. Holders of the grant are serialised within a process by a lock held for the guard's life (Task 10 review, Minor 7); two processes running the ignored suite at once are unsupported. Until a stronger mechanism ships under the contract, the VM gate must **not** read "the harness cannot read `%USERPROFILE%`" into the fence above: the harness process runs under the interactive user (or the service account), bounded by the Job Object and Claude Code's own permission fence, and no OS-level filesystem isolation is claimed.
- **The pipe as the same user.** The daemon's endpoint admits every process running as the interactive user, and `ctx_for` makes each of them the operator: a machine principal (`cli`) at **Personal** clearance, strictly above the harness clearance (Business, no third-party). A harness child that opens the pipe — the endpoint is in its `mcp.json`, and nothing OS-level stops a process it spawned or a compromised binary from dialling it — can therefore act as the operator (`task.show`, `task.create`, `task.step`, `harness.run` on other tasks, `ledger.tail`), and, because the node device key sits in the interactive user's OS keyring by default, mint a human presence proof and `approve`, `stop` and `resume`. The harness clearance binds the `harness.*` syscalls, not the process. This is the **SP1a trust model — the interactive user is the operator** — and it is in force today; nothing in SP1b ends it. A passkey (Task 5) adds a second human key and does **not** retire the node key, and no revocation is scheduled, so while the node key is enrolled a same-user process can still sign with it. The service account and the pipe DACL (Task 6) keep *other* local users off the endpoint, not this user's own processes. What would separate the harness from the user is the execution context contract above, improved after the MVP: no OS-level separation of a deliberate step is in force. The model ends only when the node key is revoked or kept out of the interactive user's keyring, and the harness runs separated from the user at the OS level. The model itself has no socket tool, so under the fence above this takes a helper or a compromised binary; it is stated because that is exactly what a TCB statement is for.
- **The lease token (Ruling 21.2).** A run's authority is a 32-byte random base64url secret, minted at launch, held in memory by hash and mapped to the run's lease id; it stops resolving the moment the run settles, however it settled, and at every daemon boot. It is written to the run's `mcp.json` and nowhere else — never to the ledger, a log line, a payload or a `--dry-run` answer, all of which carry the lease id. One run per task at a time: a second `harness.run` for a task whose run is live is refused. What a run may attach is capped at 2 MiB per file and 16 MiB per run; a breach fails the step naming the file.
- **Process.** The tree is launched under the Job Object governor (`JobGovernor::new(2 GiB, None)`): it dies when the kernel's handle closes and is capped at 2 GiB. `claude.exe` is launched directly — the binary is the daemon's configuration (`vkd --harness-bin`), never a request field, and a bare name resolves to the `.exe`, never a `.cmd` shim — and contained immediately after spawn; `governed: true` is claimed only on a verified `IsProcessInJob` read-back (Ruling 18). On Windows a child the governor cannot contain is killed before it runs and the step fails `not contained` (Ruling 21.8); on the platforms with no governor the run proceeds `governed: false`, said so. A Job Object kill leaves the child's exit status `0`, so the harness records `killed by governor` / `timeout` from what it did, not from the code. The Job Object bounds memory and lifetime; it is not a sandbox around what the process does.
- **Network egress is observed, not blocked — and the record is a lower bound.** `netwatch::sample` reads the launched pid's established TCP connections (`GetExtendedTcpTable`, IPv4 and IPv6) every 500 ms into the run record, appended to the ledger as one `harness.connections` event per run (founder decision 2026-09-24). It is telemetry, not a firewall — a confined network namespace is later-sprint work — and it has three blind spots: it is keyed by the *owning pid*, so a helper process's connections are not seen; a connection shorter than the 500 ms interval (one POST of a few KB) can complete between samples and never appear; and UDP/QUIC is not read at all. So the record can show that the harness *did* reach something, never prove that it reached nothing else. What egress is *expected* is Anthropic's servers (`api.anthropic.com`, seen in the real runs) and Claude Code's own telemetry; an address outside that set in the record is the signal.
- **The workspace.** The harness sees a label-projected directory, `<state_dir>/harness/<task_id>/`, not the store: only the register's goal (`TASK.md`), its decisions (`PLAN.md`), and the evidence artefacts whose label *flows to* the harness clearance (`BRIEF/`) are written into it — each projection recorded on the ledger (rides `infer.projected`, no new event kind), each artefact above the clearance refused. `0700` on Unix keeps *other users* out of it; on Windows it inherits the state directory's ACL — the interactive user's own under `%LOCALAPPDATA%`, and under the service the three accounts of the Task 6 section below — it is not what keeps the harness in. Its writes land in `OUT/`; what the kernel collects is what the harness attached explicitly plus the declared `OUT/<artefact_type>.*`, then the workspace is removed (a `--keep` one is swept a day after its run by the daemon's hourly retention sweep, and at the next boot whichever comes first — the same sweep that removes per-call usage rows older than the ledger's ninety-day operational class). A STOP on scope `node` kills a running harness; other scopes are recorded and halt nothing, as for the rest of the scheduler.

## The endpoint and the store under a service account (SP1b, Task 6)

`vkd-service` runs the daemon as the virtual account `NT SERVICE\vkd`, which Windows creates and manages from the service's own name: no password stored anywhere, and a Credential Manager of its own, so the master key and the node's device key are not in the founder's. Everything below is what that separation rests on, and where it stops.

- **The endpoint's access list is written out, always.** Every pipe `vkd` creates carries an explicit DACL — under the service `D:(A;;GA;;;<the service's token SID>)(A;;GA;;;<--user-sid>)`, and started by a person `D:(A;;GA;;;<that person>)`, on the default endpoint and on an explicit `--endpoint` alike. The service's own half is read off its process token at bind time, so it is right whatever account the service is configured to run as; `vkd-service install` predicts the same string from the service *name* (the `S-1-5-80-…` derivation `sc.exe showsid` prints) and the two are compared in the founder's run. The alternative is the OS default, measured on this machine as `D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<creator>)(A;;FR;;;WD)(A;;FR;;;AN)` — **Everyone and Anonymous with read**. `--user-sid` is resolved with `LookupAccountSid` and must be `SidTypeUser`: a group SID (`S-1-1-0` is Everyone and is perfectly well-formed) would otherwise hand the endpoint to everybody in it while every printed line still looked right. A descriptor the OS cannot read fails the bind; no pipe is left on the name. **Which** name: the service binds the *interactive user's own* endpoint (`\\.\pipe\vk-<their account>`, resolved from `--user-sid` through the one function `default_endpoint` uses), not a machine-wide one — a founder decision, so that `vk` needs nothing configured. It follows that a daemon that person started themselves and the service compete for one name, and the second to start is refused rather than joining the first; `--endpoint` overrides, at the cost of having to tell `vk` too.
- **The store's directory too.** `%ProgramData%\VerticalAI\vk` is created with a **protected** DACL (`D:P`, so nothing is inherited from `%ProgramData%`, which hands down Users read *and* create) granting Full Control to the service account, SYSTEM and the local administrators, `OICI` so every file and directory under it — the ledger, the register, the blobs, the harness workspaces, the log — carries the same three entries. Its **parent**, `%ProgramData%\VerticalAI`, is made the same way: left on the inherited ACL it is a directory any local account can create first, and the `CREATOR OWNER` entry it would inherit carries `FILE_DELETE_CHILD` — enough to rename the protected leaf out of the way without ever being able to read it. A directory that is already there is **audited, not adopted**: its owner and its every ACE must name one of those accounts, or the node refuses to start and says which one stopped it. The list names `NT SERVICE\vkd` explicitly as well as the account making the call, so a service and an elevated hand-run daemon accept each other's directory. That is what closes the pre-creation case, which no after-the-fact `SetSecurityInfo` could: any local account may create `C:\ProgramData\VerticalAI\vk` before the service first starts, and would then own everything written into it.
- **Who is on the other end.** A DACL says who may *open* a pipe; it says nothing about who *created* it, and the named-pipe namespace has no create-time permission — any local account can claim `\\.\pipe\vk-<user>` — the name the service binds for the interactive user it was installed for — before the service does. Two halves: the server refuses to start on a name somebody already serves (`FILE_FLAG_FIRST_PIPE_INSTANCE`), naming the holder's pid and account; and a client, after connecting, reads the **pipe object's owner** off its own handle (`GetSecurityInfo(<client handle>, SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION)`) and refuses to speak to anything that is neither its own account nor `NT SERVICE\vkd`. The owner, not the server process's token: an ordinary `OpenProcess` on a *service* is denied to an ordinary user (`ERROR_ACCESS_DENIED`), and so is one on a second standard user's process, so a process-based check would have been inert in both of the cases this exists for — while `READ_CONTROL`, which is what reading the owner needs, rides in every access mask a client can open a pipe with. **Residual:** a squatter that strips `READ_CONTROL` from its own pipe leaves the owner unreadable, and the client then connects anyway and logs it at debug, because refusing on an unreadable owner would make the shell unusable rather than safer. Closing that needs an authenticated handshake over the pipe, which is not scheduled.
- **The `ImagePath` is part of the TCB.** The registered binary runs as the service account at every start, so a binary the founder's own account can rewrite makes the separation nominal. `vkd-service install` refuses a path inside a user profile or a synced folder; the binaries belong somewhere only administrators may write (`%ProgramFiles%\VerticalAI\`), which is what `scripts/spike-6a.ps1` does. Signing them is Task 9's gate, and until it lands nothing verifies *what* is at that path — only who may change it.
- **Which ceremonies work under the service (final review I-2).** The read verbs need none. Every human verb signs with the node's device key, and the only key a node enrols is the one its daemon enrols at start with `--auto-enroll-node` — from `--node-key-file`, or from the *daemon account's* keyring, which under the service is `NT SERVICE\vkd`'s and not the interactive user's. So: a service installed without `-- --node-key-file <path> --auto-enroll-node` has **no** human key and refuses every ceremony (and, having none, cannot enrol a passkey either, since enrolment takes a presence proof); one installed with them works for a user whose `VK_NODE_KEY_FILE` names the same file, and that user can then enrol a passkey and approve with it. The shared file is a human key in a file: whoever can read it is the human, and nothing checks its Windows ACL. `vk` never mints a key (it loads one, and refuses with the remedy when the account has none or the node has not enrolled it). Not run against a live service in SP1b; a node-key provisioning design for the interactive user is the next sub-project's.
- **What the service account does not separate.** The passkey pages are still loopback HTTP on `127.0.0.1:7734` and `[::1]:7734`, and loopback has no ACL: what protects them is unchanged (both families held, single-use link tokens minted only over the endpoint, the `Host` check) and is now the *only* thing that does, since the endpoint's DACL does not reach them. The harness still runs as the service account rather than confined within it (Task 10 group G). And a local administrator remains able to reach everything here, by design: they can read the store's DACL off the object, take ownership, or reconfigure the service.
- **The DEK format broke in SP1b (Ruling 38).** Each subject's data-encryption key is wrapped under the master key with the **subject id as associated data** (SP1a review N4, Task 10 group A): a `.dek` moved or copied between subjects does not unwrap, and a `shred` verifies the key is the subject's own before it removes it. A state directory written before that — any SP1a-era store, and the SP1b demo stores made before the change — does not open its subjects: `get`/`put` fail, `shred` refuses, `vk fsck` fails the `keys` tier, each naming the three causes it can be (written before SP1b's subject binding, moved between subjects, wrong master key). There is no legacy read path, no empty-AAD probe and no migration, on purpose: no production store exists, and such a directory is recreated.
